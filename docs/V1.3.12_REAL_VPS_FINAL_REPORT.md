正式 v1.3.11 进入 Stage 1 后，drop-in 已写入 `PermitRootLogin prohibit-password`，`sshd -T` 显示 `without-password`。程序按字面比较关键字，在二次确认前提前退出：`Stage 1 未保持预期的 PermitRootLogin=prohibit-password`，退出码 1。

回滚单元名是 `vps-init-ssh-rollback-1791174410-104380`。名字只含字母、数字和短横线，没有字面量 `$`。10 分钟计时器仍已武装。journal 记录它在 04:37:11 UTC 由 systemd 启动，04:37:12 正常退出。没有手工执行回滚脚本。瞬态单元随后消失。这次不能算通过，因为 Stage 1 没有走到“等待确认，超时后回滚，再重新验证”的完整成功路径。

## 16. 端口暴露

UFW：active，默认拒绝入站，只放行 22、80、443 的 TCP，IPv6 同样这三项。没有 16601 规则。INPUT 策略是 DROP。

Lucky 管理进程监听 `*:16601`。这是进程绑定，不是防火墙放行。

重启后从跳板：

- `bash /dev/tcp` 连 16601：超时，判定不可连接。
- curl `http://107.175.44.243:16601/`：8 秒后连接超时。
- 1443、2096、8443、34556、18080、5700 也不可连接。
- 22 和 443 可连接。

重启前在测试机上用 `AF_PACKET` 抓 16601：看得到来自跳板 `38.95.76.2` 和 `172.104.83.30` 的 SYN，看不到本机发出的 SYN-ACK。Windows 上的 curl 在约 5 秒后报告 empty reply，同时本机代理指向 `127.0.0.1:7897`。抓包说明这些 SYN 没有完成握手。公网不能直接访问 16601。

设计为 loopback 的端口没有公网监听：

| 端口 | 绑定 | 重启后跳板 |
| --- | --- | --- |
| Reality 1443 | 仅在 reality/nginx/lucky-reality 时出现，且为 127.0.0.1 | 不可连接 |
| 订阅 2096 | reality-only 时公网开放是该 Profile 的设计；lucky-web 未监听 | 不可连接 |
| 面板 34556 | 127.0.0.1 | 不可连接 |
| Lucky HTTPS 后端 8443 | lucky-reality 时为 127.0.0.1 | 不可连接 |
| landing 18080 | `vps-init-landing.service`，`127.0.0.1` | 不可连接 |
| Docker 5700/18081/18082 | 127.0.0.1 | 不可连接 |

80 在 UFW 中放行，但 lucky-web 没有进程监听 80。这不是内部端口暴露。

## 17. systemd failed units

重启后 `systemctl --failed` 仍然只有：

`systemd-networkd-wait-online.service`

它由 netplan 的 drop-in 执行 `systemd-networkd-wait-online -i eth0:degraded`。这台机器的网卡是 `ens3`，状态是 routable / configured，没有 `eth0`。服务因此等待超时。SSH、ping、HTTPS 和部署都正常。`systemctl is-system-running` 显示 degraded，原因就是这一个单元。

它在本次每个 Profile 前后都存在，vps-init 的防火墙和 Profile 切换没有新增别的 failed unit。判定为云镜像 / netplan 的既有问题，**BASELINE**，不计 FAIL。

## 18. 发现的缺陷

### 已修复：SSH Stage 1 把 OpenSSH 别名当成失败

- 根因：v1.3.11 要求 `sshd -T` 的 `permitrootlogin` 字面等于 `prohibit-password`。Ubuntu 24.04 / OpenSSH 9.6 输出 `without-password`。Stage 1 在计时器已经武装后退出，走不到二次确认。
- 复现：RackNerd，正式 v1.3.11，`vps-init apply`。单元名本身是合法的，所以这不是 v1.3.10 那个字面量 `$` 问题的复发。
- 修复：`permitrootlogin_matches_expected` 把 `prohibit-password` 和 `without-password` 视为同一 key-only 策略，仍然拒绝 `yes`。drop-in 继续写 `prohibit-password`。
- 证据：行为测试和当时的 `verify/selftest.sh` 在 Ubuntu 24.04 上通过。PR CI 与 main CI 通过。Release v1.3.12 构建成功。测试机更新后，第 6 节的 10 分钟真机回滚通过。

没有发现第二个需要改代码的缺陷。下面这些不是产品缺陷：

- qinglong 的旧 nginx 站点占用 8443。当前源码不生成它。已从 `sites-enabled` 移除后重测 lucky-reality。
- apt 退出 100 是 dpkg 锁，来自 `unattended-upgrades`。
- `/zhg` 的 302 是 Lucky 斜杠重定向。
- `systemd-networkd-wait-online` 等待不存在的 `eth0`。

## 20. 最终结论

**READY WITH KNOWN NON-BLOCKING ISSUES**

v1.3.12 满足封版要求的功能项：

- 五个 Profile 都在当前正式版上完成 deploy、verify 和第二次 apply/verify。
- SSH 自动回滚真实等待约 10 分钟，由 systemd 触发，并完成第二次登录确认。
- 重启成功，boot id 改变，重启后 verify/status/info/gateway 通过，外部 HTTPS 仍可用，新 SSH 会话可用。
- Lucky 用户反代、Http3、Basic Auth、SafeURL 和密码哈希保持不变。
- Docker 用户字段在 `log-driver=local` 时不被改成 `json-file`，原 `json-file` 配置也能原样保留。
- Cloudflare Token 的 MOCK 临时故障和真实 Zone 校验都不会改写 Token 文件。
- Lucky 证书失败路径不删除旧证书，相同证书不会重复上传。
- IP 证书 SAN 等于当前公网 IP，不匹配的 SAN 不会被接受。
- lucky-web 连续三次 apply/verify 通过，没有 full upgrade，也没有无故重启 SSH socket。
- 16601 以及各 loopback 端口不能从跳板完成连接。抓包没有 SYN-ACK。
- 没有新的、无法解释的 failed systemd unit。

不把结论写成干净的 READY，是因为还有这些非阻塞事实：

1. `systemd-networkd-wait-online.service` 继续失败。它等待 `eth0`，实际网卡是 `ens3`。网络可用。这是镜像基线。
2. `https://lucky.231662.xyz/zhg` 第一跳是 302，`/zhg/` 才是 200。
3. lucky-reality 的第一次 verify 被环境里的旧 nginx 站点挡住；清掉站点后的正式重跑通过。该站点不是 v1.3.12 生成的。
4. 一次额外 apply 曾因 dpkg 锁退出 100。规定的三次 lucky-web 重跑没有失败。

未测项：没有。端口 80 在 lucky-web 下没有监听，只确认了防火墙放行和外部不可连到一个空端口，没有再为它做 HTTP 语义测试。Windows 对 16601 的 curl 不能单独当作公网可达，原因是本机代理；公网结论来自跳板和抓包。
